# Dual-OS Markers and Workspace Boundaries — Proposed Correction

**Authority context:** Design Orchard LLC  
**Audience:** Public-safe architectural description only (actual host account names, paths, permissions and machine configuration are private)  
**Recorded:** November 7, 2026  
**Status:** Human-reported mapping; implementation and access boundaries not independently verified  
**Scope:** Naming, display markers, logical responsibilities; not host reconfiguration, OS promotion or website SEO deployment

## Proper system names

- **`DrMarchand’s OS™`** is the private operating system identity. The former decorated branded name that inserted the infinity symbol into this title is **forbidden** for current display, SEO, and new documentation. Keep historical occurrences only as labeled history, not current names.
- **`Design Orchard OS™`** remains the separate public, company-wide interface identity.
- The two internal marker forms **`♾️ OS`** and **`∞ OS`** are not substitutes for either branded OS. The distinction between emoji and text symbol is intentional and should survive Unicode normalization, substitutions, search aliases and SEO generation.

## Dual-system pair inside the OS architecture

| Internal visual marker | Machine-level kind | Architectural role |
| --- | --- | --- |
| `♾️ OS` (emoji) | Dedicated local user-account context | Boundary for the Infinity Bridge |
| `∞ OS` (text symbol) | Root system workspace folder | Controlled workspace where qualifying components can be admitted and maintained |

The **literal operating-system username** and **literal local directory name and absolute path** are intentionally withheld from this public file. They must be resolved exclusively from reviewed private host configuration. Do not copy the hidden identifiers into websites, screenshots, public repository documentation, JSON-LD, diagnostics, or telemetry.

The pair is a *dual-system construction within the broader two-OS architecture*. A user-account boundary and a filesystem workspace are different object types: the marker is a display identity; the actual account is a host principal; the actual folder is a filesystem object. They must never be conflated with a third public operating system.

## Controlled lifecycle

- Private development and testing may occur **outside** the controlled workspace.
- Work that meets explicit quality, compatibility, security and authorization checks may be **admitted** into the controlled workspace, with source revision, permission and checksum recorded.
- Work that is failing or unsuitable may be **withdrawn or quarantined** from the controlled workspace without automatic deletion of its evidence or automatically renaming/removing a host account.
- No object is accepted, rejected, published, deleted or made publicly accessible solely because of a successful test or an emoji/symbol label.
- The account context and folder naming do **not** prove isolation: confirm actual ownership, ACLs, symlink behavior, process identity, sandbox boundaries, and whether services cross that boundary before claiming they are secure.

## Reconciliation against historical wording

An older doctrine described one glyph as a public build and the other as a private root. The latest human clarification identifies concrete and **different object types**: an account/boundary and a root workspace folder. Do not carry the prior public/private glyph mapping forward as if it were a verified filesystem topology. Preserve its original record as historical evidence, flag the mismatch, and reconcile the exact public-build export path and private-root relationship separately.

Likewise, **INFINITE Bridge** and **INFINITY Bridge** must not be invented as two new deployed network gateways merely from these symbols. The user has specified an **Infinity Bridge boundary** at the account level; any other bridge function, cryptographic publishing mechanism, network federation, or registry-alignment path remains separately defined and evidence-gated.

## SEO and privacy guard

Show the actual site/system names in public metadata. **Do not** expose local usernames, folder names, internal roots, SSH aliases, credentials, server mappings or invented runtime capabilities. A public page about the OS should identify `DrMarchand’s OS™` (private OS discussed publicly) or `Design Orchard OS™` (company public OS) according to its actual subject, and never represent the internal markers as separate marketable products or people.

## Evidence needed before technical enforcement

Verify, through a *private* host inspection: user-account existence and type, account-to-bridge permission scope, workspace folder existence, ownership and ACLs, symlink and mount behavior, admission/quarantine/rollback procedure, recorded failures, exact external build path, source-control mapping, and a work-specific authorized-human decision. Capture restricted receipts in appropriate custody; no live host change is authorized by this note.
